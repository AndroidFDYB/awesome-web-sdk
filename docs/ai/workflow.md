# 开发工作流规范（Superpowers 理念）

> 本文档将 Superpowers 方法论适配到 MP-SDK 工程：任何创造性工作（新功能、修改行为、修复缺陷）开始前，MUST 先完成"分类 → 设计 → 批准"三步，未获人类伙伴批准前 MUST NOT 写任何实现代码。

## 1. 三路径分类

收到开发请求的第一件事：**先分类并说出分类结果**，让人类伙伴可以纠正你。拿不准时选更重的路径——棘轮单向：任务中途发现隐藏复杂度，必须停下、说明并升级路径；任何路径中途不降级。

| 路径 | 判定标准 | 产出 | 仪式量 |
|------|----------|------|--------|
| **Spike（探针）** | 可行性问题："能不能……"、"快速验证一下就行" | 一个答案/建议，不是保留的代码 | 2-3 句话说明探针计划，点头即可 |
| **Bounded（有界）** | 改动已存在于仓库中的明确流程：一个 flag、小接口、单文件修复 | 聊天中的简短设计 + 实现 | 几句话到几段话 |
| **Architectural（架构级）** | 新子系统、重组组件关系、改变他人依赖的接口 | OpenSpec change（proposal/specs/design/tasks） | 完整流程 |

**MP-SDK 专属判定补充**：
- 触及 `specs/proto/channels.proto`（唯一真相源）→ 一律 Architectural
- 三端行为不一致的修复 → 至少 Bounded，涉及协议格式则 Architectural
- 仅 `output/` 产物或文档勘误 → 无需分类，直接做

## 2. 反模式警示

| 念头 | 现实 |
|------|------|
| "这个太简单，不需要设计" | 简单意味着设计短，不是没有设计。聊天里两句设计 + 批准，一样不能少 |
| "我标成 Bounded 就能跳过规范" | 想用标签跳过工作本身就是疑问信号——选更重的路径 |
| "设计很明显，我先写着，他们看着" | 门是"批准"，不是"设计文档的长度"。先展示，再停下等明确的同意 |
| "探针能跑了，那就把代码留下吧" | Spike 的产出是答案。保留代码是新的请求——重新分类 |
| "长出来了，但我快做完了，不用重新分类" | 中途冒出的复杂度必须升级路径。停下，说明 |

## 3. Bounded 路径流程

1. **探索工程上下文** —— 读相关文件、文档、最近提交
2. **澄清关键问题** —— 一次一个问题，只问影响方案的
3. **聊天中呈现简短设计** —— 改法、涉及文件、验证方式
4. **获得批准** —— 停下等待明确同意；展示设计与开始实现在同一口气息里完成，等于跳过门
5. **实现** —— 走正常开发流程（构建验证标准照常适用），不产出计划文档

## 4. Architectural 路径流程（接入 OpenSpec）

1. **探索工程上下文** —— `openspec/specs/` 主规范、`specs/Design.md`、最近归档的 changes
2. **澄清关键问题** —— 一次一个，聚焦目的 / 约束 / 成功标准
3. **提出 2-3 个方案** —— 带取舍与推荐理由；YAGNI 无情砍需求
4. **分节呈现设计** —— 每节确认后再继续；覆盖：架构、组件、数据流、错误处理、测试
5. **创建 OpenSpec change** —— 使用 `/opsx:propose`（或 `openspec new change <name>`），生成 proposal / specs（增量）/ design / tasks 四类 artifact
6. **自审规范** —— 检查占位符（TBD/TODO）、内部矛盾、范围是否需要拆分、二义性；就地修复
7. **人类伙伴审阅 change** —— 等待批准；有修改则回到第 5 步更新 artifact
8. **执行** —— 使用 `/opsx:apply` 按 tasks.md 实施；实现中发现偏差 MUST 回写 artifact 而非默默偏离
9. **归档** —— 全部任务勾选且构建验证通过后 `/opsx:archive`，增量合并回主规范

## 5. 实施期纪律

- **构建验证即完成标准**：每端改动执行对应 `npm run build:*`，看到成功标志才能勾任务（详见 [harness.md](harness.md) 测试军团）
- **TDD 优先**：SDK 核心模块（bridge / data-sync / emitter）的行为改动，先写失败测试再实现；无法自动化测试的端（真机依赖），以构建验证 + 场景清单人工核对替代
- **小步提交**：每个任务或任务组一个提交，提交说明写解决了什么问题
- **发现偏差回写规范**：实现与 specs 增量冲突时，先修 specs 再继续；规范是契约，代码是契约的一种实现
- **组合模式红线**：Android / 鸿蒙端禁止恢复继承式 WebView 用法（见 `specs/Design.md` §2.6/§2.7）

## 6. 工件存放约定

| 工件 | 位置 | 说明 |
|------|------|------|
| 行为规范（真相源） | `openspec/specs/<能力域>/spec.md` | 系统当前行为的唯一真相 |
| 进行中的变更 | `openspec/changes/<name>/` | proposal / design / tasks / specs 增量 |
| 已归档变更 | `openspec/changes/archive/` | 保留完整决策上下文 |
| 架构决策记录 | `specs/Design.md` + `specs/Wiki.md` | 实现层决策与演进历史 |
| AI 协作规范 | `docs/ai/` | 本文档与 harness.md |
